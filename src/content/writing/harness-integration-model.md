模型返回一段 JSON，并不表示它已经产生了一份可以执行的指令。响应可能被截断，工具名可能错误，参数可能夹带应用不应接受的控制字段。

本篇把模型放在明确的提案边界内。配套适配器只生成一份候选工单，整个实验采用单动作固定流程，没有实现开放式多轮 Agent Loop。

## 先把供应方响应与业务动作分开

Anthropic 客户端工具通过工具定义描述名称和输入结构，模型可以返回 `tool_use` 内容块；实际执行由应用完成。[工具使用说明](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)

实验给模型的工具叫 `propose_review_ticket`。它不会直接映射为一次 MCP 写入，而是先经过以下收敛过程：

| 检查 | 接受条件 | 不满足时 |
| --- | --- | --- |
| 停止原因 | 完整的 `tool_use` 提案 | 不执行写入 |
| 调用数量 | 恰好一个允许的提案 | 拒绝多提案 |
| 工具名称 | 与提案工具一致 | 拒绝其他工具 |
| 输入字段 | 仅有 source 与 title | 拒绝额外字段 |
| 字段内容 | 非空字符串，长度在本地上限内 | 拒绝畸形参数 |
| 任务约束 | 与可信测试目标完全一致 | 记录提案失败 |

“恰好一个”是本实验的应用策略，不代表模型接口不能返回多个工具调用。这里收窄自由度，是为了先验证执行边界。

## 停止原因决定能否进入下一阶段

正常结束、工具调用和达到输出上限是不同状态。不能因为已经看见部分工具参数，就忽略整体响应的停止原因。[停止原因文档](https://platform.claude.com/docs/en/build-with-claude/handling-stop-reasons)

实验对 `max_tokens`、普通文本结束和错误工具名分别保留反例。失败时没有“猜测修复后继续创建”的分支。

适配器使用非流式请求。它没有验证增量工具参数、流中断、重连或片段重组。未来增加流式体验时，可以先展示生成进度，执行仍应等待完整解析和业务校验通过。

## 业务目标必须来自另一条可信输入

本实验的目标是固定来源与固定标题，模型提案必须精确匹配。这个任务很简单，不能测量模型研究能力；它让“模型改了目标”成为容易检查的错误。

如果把模型提案原样复制成期望结果，再拿两者比较，验收一定通过，却无法发现目标偏移。真实任务可以采用更复杂的验收器，但任务目标和候选结果仍应有独立来源。

`approved`、`operation_key` 等额外字段会被拒绝。模型不能通过自报“已批准”取得本地执行资格，也不能自己换一个操作键绕过去重。

## 在线适配器的边界

可选模式向 Anthropic Messages API 发送一次合成测试任务，使用调用者显式提供的模型标识和环境变量中的密钥。请求设置输出上限、网络超时和响应体大小上限，没有自动重试或模型降级。

默认回归不会调用这条远端路径。当前已验证的是解析器、缺少配置时不发送请求，以及固定提案如何进入真实 MCP 链路。真实模型可用性、费用、限流和延迟均未实测。

在线请求若失败，实验只打印错误类型，不把请求头或原始服务端错误正文写入输出。这减少意外泄漏，但也限制了诊断细节；正式接入应建立经过脱敏的错误分类，而不是把所有失败统一叫网络错误。

## 保存提案之后，恢复不再重新问模型

一旦候选动作通过检查，Harness 将它写入运行库。后续相同运行的恢复直接使用保存的动作，从而避免重连后模型生成不同标题或新意图。

如果进程在模型返回后、保存前退出，恢复仍可能重新请求模型。当前实验没有持久化模型请求预算，因此不保证跨崩溃只调用模型一次。这与已持久化的写入派发预算是不同范围。

[模型网关篇](/writing/harness-operations-model-gateway/)讨论了路由与成本。本篇建议先留下供应方、返回模型标识、响应 ID 和 usage，再讨论自动重试和降级；没有证据时，不把“接口可调用”写成“成本已经可控”。

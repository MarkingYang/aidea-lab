模型模块的职责是提出下一步；运行器负责决定这一步能否发生。要把两者拆开，先约定输出结构，再接供应方 API。

## 从任务契约构造上下文

工单实验的可信目标只有两个字段：

```json
{"source":"source-001","title":"核验 Agent Harness 资料"}
```

运行 ID、数据库位置、执行开关和派发预算由应用另外保存。它们不属于模型可以改写的参数。上下文组装器在这个阶段只需要任务说明、目标字段和可用工具定义。

扩展为资料研究任务时，按四层组织输入：稳定的任务规则；当前用户目标；带来源标识的材料；本轮状态和最近工具结果。检索材料中的指令应按资料内容处理，不能用它改写执行策略。长输出保留摘要与可重新读取的引用，原始证据另存；不要把每轮日志全部追加进去。

默认先用显式消息列表。只有在真实任务中发现“相关材料找不到”或上下文预算不足，才增加检索、压缩或分层记忆。这样可以判断收益到底来自模型、材料还是运行逻辑。

## 模型适配器输出什么

实验中的实际接口是：

```python
# model.py 中已有的接口；provider 默认为 fixture
propose(expected, provider, model) -> (action, metadata)
```

`action` 必须恰好包含非空的 `source`、`title`，每项长度不超过 300 字符。`metadata` 保存模型来源；在线模式还记录响应 ID、模型和用量，便于排查同一动作是怎样产生的。

`parse_response()` 检查停止原因是 `tool_use`，且恰好出现一个名为 `propose_review_ticket` 的工具调用；随后由 `validate_action()` 检查字段。运行器最后把动作与可信目标比较。Schema 正确只能说明结构合规，不能证明目标正确。

| 模型返回 | 处理方式 | 理由 |
| --- | --- | --- |
| 一份完整、字段正确的提案 | 保存后进入运行器 | 提案获得了明确结构 |
| 普通文字“已创建” | 拒绝 | 没有可执行提案，也没有资源证据 |
| 被 token 上限截断的响应 | 拒绝 | 不能按部分输出猜测动作 |
| 两个工具调用 | 拒绝 | 超出本实验单动作契约 |
| 增加 `approved` 或 `operation_key` | 拒绝 | 模型不能扩充自身权限或改变去重标识 |
| 字段合法，但标题与目标不同 | 运行器拒绝 | 结构正确仍可能做错任务 |

新项目可用供应方官方 SDK 处理连接与响应类型，但应保留这层应用契约。工具名称、用途说明和输入 Schema 是模型选工具的依据，名称对上并不足以约束参数语义。[Claude 工具定义文档](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)

## 多轮 Agent Loop 应怎样接

如果任务需要“读材料以后再决定查哪里”，单次 `propose()` 就不够。推荐把适配器扩展为接收消息历史和本轮可用工具，返回统一的三类结果：候选工具调用、最终答案、无法继续。循环控制不依赖供应方具体的停止原因名称。

下面是设计伪代码，展示模块连接；它不是实验包中可直接调用的 API：

```text
读取已保存的任务、状态和消息
重复，最多 N 轮：
    检查任务截止时间、剩余额度和取消状态
    组装本轮上下文，调用模型，校验完整响应
    若模型提出最终答案：执行独立验收，再决定成功或继续
    若模型提出工具调用：
        校验工具与参数，检查当前执行权限
        为业务动作确定稳定操作键，保存意图与预算消耗
        对结果未知的历史写入先查询资源
        仅在可以安全执行时派发工具
        保存工具结果，按供应方协议关联原 tool call ID
        将模型的调用消息与对应工具结果加入下一轮上下文
    若无法继续：保存原因并退出
轮数耗尽：保存 budget_exhausted，交给用户或后续流程
```

最容易遗漏的是工具结果回传。只调用工具再打印结果，不构成“观察结果后再决策”的循环。另一处是身份：供应方的 tool call ID 用于消息关联，业务操作键用于副作用去重，两者不能混用。一次写入在重试时应复用同一业务键；不同业务动作必须分配不同键。

## 预算怎样放进组合

至少区分模型请求次数、工具派发次数和任务总截止时间。模型超时、工具超时、任务超时也要分别处理。写入超时可能意味着结果未知，应进入对账流程，不能一律重试。

配套实验已经持久化工具派发预算，上限为 2；模型适配器是一次非流式请求，尚无持久化模型预算、多轮消息或总截止时间。扩展循环时先补这些控制，再增加自动重试；否则一次重启就可能重置额度。

## 先换模型，保持其他模块不变

默认 `fixture` 返回固定响应，用来稳定测试运行器；`anthropic` 是可选的在线提案适配器。两者输出同一份动作契约，因此工具、存储和验收可以复用。

选模型时，用同一批任务比较合法提案率、目标符合率、完成成本和延迟。格式经常出错时先检查 Schema 与工具说明；提案正确但资源错误时检查执行和验收。不要把所有失败都归因于模型能力。更多网关设计见[模型网关](/writing/harness-operations-model-gateway/)。

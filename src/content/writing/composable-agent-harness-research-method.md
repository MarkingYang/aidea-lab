不同项目可以独立研究，但不能使用完全不同的证据口径。否则最后得到的不是知识体系，而是十篇风格各异的产品介绍。

## 每个系列固定四层

第一篇先搭全景，只回答定位、边界和主数据流。中间篇进入源码或规范，沿一次真实任务追踪输入、模型、工具、状态与结果。随后检查权限、恢复、版本、扩展和维护风险。终篇不复述功能，而是提炼这个项目独有的设计判断。

```mermaid
flowchart LR
    A[官方定位] --> B[固定版本或快照]
    B --> C[追踪一条主数据流]
    C --> D[检查失败与恢复]
    D --> E[区分事实与推断]
    E --> F[形成单项目结论]
```

*图 1｜研究先固定事实，再产生判断；跨项目综合不进入当前流程。*

## 一张可复用的源码阅读卡

| 维度 | 必须留下的答案 |
| --- | --- |
| 系统边界 | 它拥有模型循环、只提供扩展，还是只是资产仓库？ |
| 状态主线 | Session、消息、工具结果、记忆分别存在哪里？ |
| 控制边界 | 谁决定继续、停止、审批、重试和恢复？ |
| 扩展机制 | Skill、Hook、Plugin、MCP 在何时加载？ |
| 信任模型 | 哪些是提示建议，哪些是运行时强制？ |
| 演进成本 | 格式、安装、兼容和退出由谁负责？ |

每篇优先引用官方仓库、官方文档和可定位源码。快速变化的数字只在确有分析价值时出现，并注明快照；官方自我描述与本文推断分开书写。这样未来更新时，可以替换失效事实，而不必推倒整篇文章。

## 图谱怎样维护

知识图谱不再把十个项目塞进一个局部圆。每个系列拥有自己的中心节点，文章只连接本系列、真实关键词和正文明确引用。母系列提供阅读入口，却不制造“项目相似”连线。等独立研究完成后，再由综合文章产生有解释的跨系列关系。

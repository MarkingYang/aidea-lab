当 Agent 只有十几个工具时，能力选择很简单：把工具描述放进上下文，让模型决定调用哪个。

但当系统接入上万个 Skill、MCP Server 和专业 Agent，这个方案就会遇到瓶颈。上下文装不下全部说明，相近能力难以区分，权限和运行状态不断变化。同一个任务还可能有多种完成方式：调用工具、加载 Skill，或者委派给另一个 Agent。

问题从“如何调用工具”，变成了：

> 如何在庞大的能力库中，以合理的成本找到合适的能力，并在授权范围内完成任务？

答案的核心很简单：**先检索，再选择；先确认，再加载；按能力类型执行，而不是把全部能力提前交给模型。**

本文结合 Deep Agents、Agent Skills、MCP Registry、ARD、Agent Finder、ToolHive 等开源项目，讨论这条链路如何落地。

> [!NOTE]
> 本文以 2026-09-04 查阅的官方文档与仓库说明为参考，是架构设计与开源实现对照，不是这些项目的部署报告，也不声称任何组合已经通过万级生产压测。项目功能随版本变化，选型时应固定版本并验证实际行为。

## 一、先分清楚：你到底在选什么？

“MCP、Skill、Agent 路由”经常被放在一起讨论，但它们不是同一种东西。

| 对象 | 本质 | 选中之后做什么 |
| --- | --- | --- |
| Skill | 完成一类任务的方法、说明和配套资源 | 加载说明，由当前 Agent 按步骤执行 |
| MCP Server | 通过 MCP 暴露工具、资源等能力的服务端 | 建立连接，发现其提供的具体能力 |
| MCP Tool | 具有参数定义的具体操作 | 校验参数并调用 |
| Agent | 能够接受任务并自主推进的执行主体 | 委派任务，跟踪状态，验收结果 |

第一，**MCP 是协议，MCP Server 才是可发现、可连接的服务实体**。找到服务器，不等于找到了任务所需的操作。

一个代码托管平台的 MCP Server 可能同时提供搜索仓库、读取 PR、创建 Issue、删除分支。用户要“查看 PR”，不能因为选对了服务器，就认为路由已经完成。

第二，**加载 Skill 不等于把任务交给另一个 Agent**。前者是“当前 Agent 按某种方法做”，后者是“另一个执行主体负责做”。

因此，系统需要统一发现入口，但不能把执行语义抹平：统一回答“有什么能力”，分别处理“怎样使用这种能力”。

还要明确“万级”的统计口径。一万个服务器、一万个工具、一万个含多个步骤的 Skill，并不是同一种负载。目录条目数影响索引与召回；并发请求数影响服务容量；连接数和冷启动影响执行时延。不能用“能存一万个条目”推导出“能同时处理一万个任务”。

## 二、按需加载已经存在，但万级规模还缺一个前置层

Agent Skills 规范将能力组织为 `SKILL.md`、脚本、参考资料和资源文件，并采用渐进式加载：先看元数据，再读取完整说明，最后按需访问附属内容。[Agent Skills 规范](https://agentskills.io/specification)

Deep Agents 的文档描述了这种默认流程：启动时将已配置 Skill 的名称和描述加入系统提示，匹配任务后再读取完整说明。它也提供动态 Skill 列表等扩展方式；这里讨论的是全量配置目录直接进入上下文的成本，而不是说框架无法扩展。[Deep Agents Skills](https://docs.langchain.com/oss/python/deepagents/skills)

这解决了“不要提前加载全部正文”，但没有自动解决“不要提前加载全部目录”。

假设每个能力摘要平均占用 100 tokens，一万个摘要就需要约 100 万 tokens。这只是容量估算，却说明一个问题：**到了万级规模，连摘要都需要先检索。**

可以在现有渐进式加载机制前面增加一层：

```text
L0：外部能力索引，不进入模型上下文
 ↓ 检索
L1：少量候选能力卡片
 ↓ 选择
L2：选中能力的完整说明或接口定义
 ↓ 按需
L3：参考资料、脚本、模板与执行依赖
```

这是面向大目录的工程扩展，不是 Agent Skills 规范自带的万级路由。

具体落地时，Agent 可以常驻少量稳定入口，例如“搜索能力”和“获取能力详情”，再保留必要的高频基础工具。它始终知道如何寻找能力，不需要始终知道所有能力是什么。搜索也可以由运行时主动触发，不必每次都多消耗一轮模型调用。

## 三、开源项目分别解决了哪一层？

这些项目不是同一类产品，也不需要全部部署。更有价值的读法，是看它们分别承担哪一层职责。

| 层次 | 开源项目 | 可借鉴的部分 |
| --- | --- | --- |
| Agent 运行框架 | [Deep Agents](https://github.com/langchain-ai/deepagents) | 上下文管理、Skill 加载、子 Agent、工具执行 |
| Skill 格式 | [Agent Skills](https://github.com/agentskills/agentskills) | 能力包结构与渐进式加载 |
| MCP 元数据目录 | [MCP Registry](https://github.com/modelcontextprotocol/registry) | 服务器发布、元数据管理和发现 |
| 跨类型发现规范 | [ARD](https://github.com/ards-project/ard-spec) | Skill、MCP、Agent 等资源的描述与联邦发现 |
| 可发现目录 | [Agent Finder Catalog](https://github.com/github/agentfinder-catalog) | 为运行时能力发现提供可维护的目录 |
| MCP 运行与治理 | [ToolHive](https://github.com/stacklok/toolhive) | Registry、Gateway、Runtime 的职责划分 |
| 统一资产治理 | [MCP Gateway & Registry](https://github.com/agentic-community/mcp-gateway-registry) | 跨类型注册、搜索、访问控制与审计 |
| Kubernetes 托管 | [kagent](https://github.com/kagent-dev/kagent) | Agent 与工具服务的部署和生命周期管理 |
| Agent 目录 | [Agent Registry](https://github.com/zfdang/agent-registry) | Agent Card 获取、协议验证和发现接口 |

这里需要守住三个边界。

**Registry 不等于智能路由器**。MCP 官方 Registry 提供服务器目录，并不自动替你完成任务理解、具体工具选择和授权执行。

**开源目录不等于开源完整搜索引擎**。`github/agentfinder-catalog` 是为 Agent Finder 提供内容的公共目录。项目明确区分“发现”和“安装”：发现能力，并不意味着静默连接它。[Agent Finder Catalog 说明](https://github.com/github/agentfinder-catalog)

**运行平台不等于选择算法**。kagent 可以管理 Agent 和工具服务，但把资源部署到 Kubernetes，并不会自动解决“哪个能力最适合这条请求”。[kagent 核心概念](https://github.com/kagent-dev/kagent#technical-details)

它们提供的是系统的不同部分，而不是装上就能保证路由准确的成品。

## 四、统一能力目录，不必统一成一个数据库

用户不应该先判断“我要找 Skill 还是 Agent”，因此可以在不同资源之上建立统一的能力描述。

一张用于路由的能力卡片，应回答：能做什么、需要什么、产出什么、何时不适用、有什么副作用，以及到哪里取得完整说明。

```yaml
# 自定义路由记录，不是某个协议的标准 Schema
id: acme/meeting-summary
kind: skill
version: "1.3.0"

description: 将会议逐字稿整理为结论、决策和待办
inputs:
  - transcript
outputs:
  - summary_document

use_when:
  - 已有文字记录，需要整理会议内容
do_not_use_when:
  - 需要将录音转写为文字

requires:
  - document.create
side_effects:
  - external_document_write

artifact_ref: registry://acme/meeting-summary/1.3.0
```

上面的 `registry://` 只是示意性的内部定位符，不是要求客户端实现的新标准协议。真实系统可以使用内容地址、受控文件路径或经过验证的 HTTPS 地址。

这些信息也不应全部由作者自报。用途描述可以来自作者；准入状态、权限判定、来源验证和运行健康，应由平台独立维护。模型生成的摘要同样需要核验，不能把推测变成接口契约。

建议把数据分成三组：

- **静态信息**服务检索：描述、输入输出、版本、依赖、来源。
- **运行信息**服务可行性判断：连接状态、当前权限、配额、延迟、错误率。
- **反馈信息**服务改进：任务成功、用户拒绝、回退原因、误选案例。

统一的是标识、查询接口和治理规则，不必是物理存储。企业可以保留多个注册中心，通过同步索引或受控联邦查询提供统一入口。ARD 正在定义面向多类 Agent 资源的联邦目录与发现方式，而不是要求所有资源进入一个中央商店；落地时需要明确兼容版本。[ARD 项目说明](https://github.com/ards-project/ard-spec)

跨目录聚合还要去重。相同资源的镜像、别名和多个版本，不应该占满候选列表。可以结合发布方命名空间、稳定 ID、版本和内容摘要识别同源条目，再保留来源信息以便追溯。

## 五、在线路由：检索缩小范围，模型处理取舍

一条可落地的链路可以是：

```text
请求与任务状态
    ↓
任务理解：目标、输入、输出、约束
    ↓
可见性与明确禁止条件过滤
    ↓
精确匹配 + 关键词检索 + 向量检索
    ↓
融合、去重、必要时精排
    ↓
方案选择与依赖可行性检查
    ↓
获取选中能力的完整定义
    ↓
最终授权与参数校验
    ↓
执行、验证、必要时重新检索
```

这不是要求每个请求都经过所有阶段。明确、低风险、能力已加载的请求，可以走短路径；候选混淆或跨能力组合的任务，再进入更完整的选择流程。

### 不要只拿用户原话做向量搜索

用户说：“把上周的客户会议整理成飞书文档，先不要发群。”

检索需要保留的不只是“会议”和“飞书”，还有时间范围、客户范围、目标产物，以及禁止发送的约束。未明确的客户范围应标记为未知，不能偷偷补成事实。

尤其不能在查询改写时丢掉“不要发群”。否则，“整理纪要并自动分享”可能成为很相关但完全不合适的候选。

### 先限制可见范围，再做相关性排序

不属于当前租户、明确禁止访问或已禁用的能力，不应仅仅降低排名。**权限不是偏好，不能用相关性抵消。**

但也不能把所有暂时不能执行的能力都归为不存在。允许使用、只是尚未登录的连接器，可以标记为“需要授权”。因此至少需要区分：不可发现、可发现但未就绪、当前可执行。

检索侧负责不泄露不可见元数据，执行端仍必须重新授权。搜索时可见不构成永久调用许可。

### 混合检索是合理起点，不是唯一答案

精确匹配处理工具名、资源 ID、产品名和用户点名的能力；关键词检索处理业务术语、文件类型和接口动作；向量检索处理自然语言与能力描述之间的表达差异。

MCP Gateway & Registry 的设计文档描述了向量与关键词结果的 RRF 排名融合方案。[混合搜索架构](https://github.com/agentic-community/mcp-gateway-registry/blob/main/docs/design/hybrid-search-architecture.md)

RRF 避免直接相加量纲不同的检索分数，但它不处理权限、风险，也不保证最优效果。明确点名应作为选择约束处理，不能只提高一点排名后又悄悄替换。面向中文请求和英文描述，还需要验证分词、别名和多语言语义召回。

### 比较方案，不只比较分数

“读取文档”工具、“文档总结”Skill 和“研究报告”Agent，都可能与同一请求相关，但任务粒度不同，分数也未必可比。

更稳妥的办法是：各类型召回保留一定多样性，将候选组织成方案，再比较覆盖范围、依赖、成本和风险。

例如实验起步时，可以让关键词与向量各召回几十个候选，合并后给精排处理几十个，再将少量卡片交给模型。候选数应由真实评测决定；模型可读 token 预算比单纯的条目数更有约束力。

一个 Agent 能完成整个任务，不意味着它一定优于两个简单工具。一个工具相关度最高，也不意味着它能单独完成任务。**最终选择的对象，经常是一条完成任务的路径。**

## 六、三类能力，三种加载与执行策略

### Skill：先读方法，再解析依赖

[skills-mcp](https://github.com/Jignesh-Ponamwar/skills-mcp) 提供了直接的参考：检索描述与触发短语，再获取完整正文，最后按需读取参考资料、资源或运行脚本。项目的分层接口有借鉴价值，但示例规模和宣传不能替代自己的生产验证。

Skill 被选中只是进入下一阶段。读完说明后，还需要检查输入条件、工具依赖、用户限制、运行环境，以及版本和内容是否与索引记录一致。

如果不满足，就换候选、补充检索或澄清。不要因为已经加载了一份说明，就坚持走到底。Skill 内容也不能提升权限：加载一个要求发邮件的流程，不意味着用户已经授权发邮件。

### MCP：服务器发现与工具选择分开

已有工具级索引时，可以直接查找具体操作；只有服务器级目录时，则先发现候选服务器，再在允许连接的范围内获取工具列表。

不能每次请求都连接上万个服务器来枚举工具。对于已批准的服务，可以在控制面缓存工具目录、版本和更新时间，在必要时刷新，并验证候选工具仍存在且 Schema 兼容。

[LangGraph BigTool](https://github.com/langchain-ai/langgraph-bigtool) 展示了“检索工具 ID，再让工具进入 Agent 可用集合”的模式。工具对象可能早已在进程里注册，动态变化的是模型可见集合，并不一定是动态下载代码。

[FastMCP Tool Search](https://gofastmcp.com/servers/transforms/tool-search) 则使用搜索和调用代理，避免向模型提供全量目录。短小的 Schema 可以随搜索结果返回，减少往返；复杂定义可以进一步分层。

按需发现不等于自动安装未知服务。对于未准入的包、容器和端点，仍需要来源审查、显式授权与隔离运行。

### Agent：选择能力，也选择委派边界

选择远程 Agent 时，需要检查任务匹配、输入输出兼容性、数据是否允许跨域，以及实际支持的状态查询、取消和结果取回方式。不能假定所有 Agent 都支持相同任务生命周期。

Agent Card 提供发现所需的信息，但不是质量证明。[A2A Agent Discovery](https://a2a-protocol.org/latest/topics/agent-discovery/)

`zfdang/agent-registry` 对 Agent Card 和协议响应进行验证，是注册阶段的有用参考。但“端点存在且符合协议”与“能高质量完成任务”是不同目标。[Agent Registry 验证机制](https://github.com/zfdang/agent-registry)

还要注意：A2A Agent Card 中的 `skills` 是能力描述条目，不应直接等同于可下载的 `SKILL.md` 能力包。框架内的子 Agent 与外部 A2A Agent 也不是同一个信任边界。

委派时应传递目标、必要输入、禁止事项、结果验收条件和预算，而不是无差别转发整段对话。限制递归委派深度与总预算，避免 Agent A 转给 B、B 又转回 A。只有完成一个独立任务确实值得承担协调成本时，才需要委派。

## 七、用一个任务看完整选择过程

继续看这个请求：“把上周的客户会议整理成飞书文档，先不要发群。”

系统检索出三种方案：

- **方案 A**：加载会议整理 Skill，使用会议读取和文档创建工具。
- **方案 B**：委派给专业会议助理 Agent。
- **方案 C**：使用“总结并群发”工作流。

首先排除无法关闭群发步骤的方案 C，它违反明确约束。

再比较 A 和 B。如果已有会议记录可读取，当前 Agent 能完成整理，A 可能依赖更少，也无需额外传输给远程 Agent。如果 B 位于可信环境，具备必要专长，并且有可接受的质量和成本证据，它也可以成为合理选择。

这里没有“永远优先 Skill”或“复杂任务永远委派 Agent”的固定答案。

假设选择 A，后续流程是：

1. 加载会议整理 Skill，核对步骤、输入条件与工具依赖。
2. 解析或确认客户范围，以及“上周”的时区和日期区间。
3. 获取会议和已有记录，确认是否拿全所需数据。
4. 生成摘要，区分原始决策和模型推断。
5. 在目标位置创建文档。
6. 验证文档存在、内容完整、位置和分享权限符合要求。
7. 返回文档链接，不发送群消息。

如果只有录音，没有逐字稿，系统需要重新发现转写能力；没有合规转写方案，就停在明确的阻塞状态。按能力缺口追加检索也是 [MCP-Zero](https://github.com/xfey/MCP-Zero) 的研究方向，但研究实现不等于完整生产控制面。

“不发群”也不代表文档可以公开分享。文档 ACL 是另一个要检查的副作用边界。

这说明能力检索不是只在任务开始时调用一次的函数，而是受约束、受预算控制的运行时能力。

## 八、生产路由必须允许不执行

如果路由接口只能返回一个能力 ID，它会诱导系统在信息不足时也做选择。至少应该把下面几种结果分开：

| 路由结果 | 含义 | 后续动作 |
| --- | --- | --- |
| SELECT | 有满足要求的能力或方案 | 加载详情并做最终校验 |
| CLARIFY | 缺少影响决策的用户信息 | 提一个具体问题 |
| NEEDS_AUTH | 能力允许使用，但需要登录或授权 | 进入受控授权流程 |
| NO_MATCH | 检索已完成，但在当前范围内未找到合适能力 | 说明搜索范围与缺口，不猜造工具 |
| BLOCKED | 策略、环境或依赖阻止执行 | 报告原因和允许的下一步 |
| NO_TOOL | 当前请求不需要外部能力 | 直接回答，不为调用而调用 |

向量相似度 0.9 不等于“90% 的概率选对”，模型自报的置信度也不是校准后的概率。需要在标注任务上评估自动选择与弃选的取舍，并对高风险操作采用更严格的条件。

失败恢复同样需要边界：参数错误可以修正，能力不匹配可以重选，临时故障可以在预算内重试。权限拒绝不能换连接器绕过；写操作超时也不能立即换工具重做，应先查询状态或使用接口支持的幂等机制，避免重复创建、重复发送。

## 九、控制面：把找到能力和允许执行分开

检索系统不应独自承担部署、凭证、权限和审计。

ToolHive 将 Registry、Gateway 和 Runtime 分开：目录管理可信服务，网关处理访问策略，运行层托管和隔离执行。身份策略需要实际配置，不能把容器隔离理解成自动具备完整授权。[ToolHive 架构](https://github.com/stacklok/toolhive#core-capabilities)

MCP Gateway & Registry 则将 MCP Server、Agent、Skill 等资产放在共同的注册、发现和治理体系中，并区分注册控制面与网关数据面。[项目架构](https://github.com/agentic-community/mcp-gateway-registry#how-it-works)

可以从中提炼四个职责：

- **Registry**：记录能力是什么、来自哪里、有哪些版本。
- **Router**：判断当前任务适合哪些能力或组合。
- **Policy**：判断当前身份是否允许使用。
- **Executor**：加载、连接、委派并跟踪执行。

这些是逻辑边界，不要求第一天就拆成四个微服务。统一控制面也不意味着所有 Agent 通信必须经过注册中心。数据走网关还是受控直连，应由网络、审计和信任模型决定；实际执行端始终需要鉴权。

还要把安全边界前移到“搜索”本身。将包含客户姓名、合同内容或内部项目代号的查询发送到公共 Registry，已经是一种数据外传。联邦搜索应有目的地白名单、查询最小化和分类策略；敏感查询不能默认广播到所有目录。抓取外部卡片和资源时，也需要防范 SSRF、恶意重定向与超大响应。

返回的描述、Skill 正文和 Agent 输出，都不应获得覆盖宿主策略的权力。来源验证、内容扫描和执行隔离可以降低风险，但不能宣称消除了提示注入。

**检索命中不是安装许可，安装成功不是调用授权，调用成功也不是任务完成。**

## 十、万级规模下，优先优化这几件事

### 元数据与依赖质量

注册时检查用途、输入输出、适用边界、副作用和重复描述。反例单独保存，供精排与约束判断使用，不必全部混进正向向量文本。

记录“服务器提供工具”“Skill 依赖能力”“Agent 支持任务”等关系，有助于补全方案。先用关系表或邻接表即可，不必一开始就引入图数据库。历史共用关系只帮助发现，不能自动授权调用。

### 上下文与搜索预算

不仅限制候选数，还要限制摘要长度、Schema 体积、完整 Skill 数量和追加搜索次数。为检索、精排、详情获取分别设截止时间，避免一个慢目录拖住整个任务。检索未完成要记录为部分结果或失败，不能与确实无匹配混为一谈。

### 缓存与版本失效

可以缓存候选、能力卡片和已批准服务的定义，但键和失效条件需要考虑租户、权限范围、索引版本及策略变化。执行时重新授权，防止权限撤销后继续使用旧结果。

固定一次任务使用的能力版本；发现定义已变化时，应重新确认兼容性，而不是让搜索描述和执行接口各用一版。

### 反馈不要放大历史偏见

成功率必须按任务类型、版本、环境和样本量解释。低频能力可能只接到困难任务，高频能力也可能只是更常被展示。不要直接用全局成功率排名，否则新能力永远没有机会进入候选，旧的误选会被强化。

探索新能力应优先发生在离线评测或低风险灰度中，而不是拿高风险写操作做在线试验。

## 十一、如何证明路由真的有效？

“从一万个候选里返回五个”只能证明会筛选，不能证明筛得对。评测至少覆盖四层：

| 层次 | 要回答的问题 | 指标示例 |
| --- | --- | --- |
| 检索 | 可接受的正确能力是否进入候选集？ | 候选命中率、MRR、分类型 Recall |
| 选择 | 方案是否满足目标与约束？ | 方案正确率、误选率、澄清与弃选质量 |
| 执行 | 输入、权限、依赖和环境是否满足？ | 校验失败率、回退率、未授权副作用 |
| 结果与成本 | 目标产物是否产生，付出了什么成本？ | 任务成功率、P95 延迟、每次成功任务成本 |

对于多步骤任务，还要评估必要能力是否全部覆盖。命中其中一个正确工具，不代表整条方案可执行。

测试集需要包含相近能力、多语言表达、明确禁止事项、缺参数、权限不足、新能力、工具定义变更，以及库中不存在答案的请求。允许多个正确方案，避免把某个工具 ID 当作唯一标准。

应将纯检索、加入向量、加入精排等方案放在同一批任务上对照，记录质量与延迟收益。把同一能力的近重复问法全部放进训练和测试，容易得到虚高结果；可以按时间、能力族或新旧版本留出测试集。

线上还需要知道“模型到底看到了什么”。MCP Gateway & Registry 的 discovery receipt 设计记录了候选、结果预算和部分被截断候选，帮助区分没搜到、搜到了但没展示。正式审计仍由服务端日志或追踪系统承担，不依赖模型保存证据。[发现记录与上下文预算](https://github.com/agentic-community/mcp-gateway-registry/blob/main/docs/dynamic-tool-discovery.md#discovery-receipts-and-context-budgets)

没有自己的测量，就不要用“支持 thousands of tools”替代端到端证据。

## 十二、落地顺序：先建立闭环，再增加组件

第一步，用统一能力卡片、精确匹配和关键词检索，把“搜索—选择—加载—执行—验证”跑通。保留无匹配、待授权和澄清路径，建立一批真实任务作为基线。

第二步，针对已测量到的同义表达漏召回和候选混淆，增加向量、混合融合或精排。针对跨能力任务，补齐依赖关系与有限规划。每加一层，都比较准确率、延迟和成本。

第三步，接入多团队或外部能力时，再加强联邦发现、来源验证、版本控制、凭证代理和运行治理。从影子路由开始验证新策略，只比较选择结果，不额外触发写操作，再逐步灰度。

现有工程栈决定借鉴顺序：已有 LangGraph Agent，可以参考 BigTool；已有 MCP 工具服务，可以参考 FastMCP；需要 Skill 内容服务，可以参考 skills-mcp；需要企业托管和准入治理，再评估 ToolHive 或 MCP Gateway & Registry。它们不必同时进入架构。

每增加一个组件，都应该回答：**它解决了哪一类已经被测量到的失败？**

## 结语：把寻找能力变成基础能力

万级 MCP、Skill 与 Agent 路由，不是让模型记住一万个名字，也不是把所有描述向量化后取一个 Top-1。

它需要一条清晰的链路：注册可信能力，检索小型候选集，比较可执行方案，按需加载，授权执行，验证结果。

开源生态已经提供了许多部分：Agent Skills 定义能力包，Deep Agents 承载执行，MCP Registry 和 ARD 组织发现，BigTool 与 FastMCP 展示动态选择，ToolHive 等平台补上运行与治理。真正需要建设的，是它们之间的连接，以及面向实际任务的策略和评测。

**一个可扩展的 Agent，不需要预先加载所有能力。它需要始终知道去哪里找、如何判断，以及什么时候不该执行。**

这里集中提供两组故障实验：并发与协议状态实验检查基础契约；业务恢复实验检查写入前后中断。两组都能下载运行，测试范围分别说明。

[下载实验包](/labs/harness-foundations.zip)。需要 Python 3.10+，只使用标准库，不需要模型密钥。

## 先运行，再对照证据

解压并进入 `harness-foundations` 目录后执行：

```sh
python3 lab.py
python3 -m unittest discover -p 'test_*.py' -v
```

包内有 `README.md`、`lab.py` 和 `test_contracts.py`。演示使用临时目录，每次运行重新创建数据库，结束后自动清理。

参考输出如下。线程竞争的获胜者不固定，但这些汇总值应保持一致：

```json
{
  "concurrent_updates_accepted": 1,
  "document_version": 2,
  "late_response": "ignored_response",
  "needs_reconciliation": ["review-001:ticket"],
  "actual_ticket": [1, "source-001"],
  "actual_ticket_count": 1
}
```

一个更新被接受，对应文档版本从 1 变成 2。随后演示先创建工单，再模拟响应丢失和重连；旧响应被忽略，实际工单仍然只有一个。

`needs_reconciliation` 仍包含操作键是有意保留的：独立查询发现工单，不会自动修改协议模型的待对账集合。完整 Harness 还应检查目标与参数，再持久化任务终态。

## 哪些部分真正执行，哪些部分受控模拟

| 层次 | 实验实际做了什么 | 没有验证什么 |
| --- | --- | --- |
| 并发存储 | 两线程、独立连接、真实 SQLite 提交 | 多机器竞争、目标数据库隔离级别 |
| 工单去重 | 唯一约束、事务内查找与创建 | 多租户身份、去重记录过期 |
| 协议状态 | Python 字典消息、等待表和受控事件 | 网络传输、完整 Schema 与协议一致性 |
| 连接中断 | 清除等待项并模拟重新初始化 | 真实 TCP、HTTP、SSE 或子进程故障 |
| 业务观察 | 读取实际提交的本地工单 | 远端最终一致性与任务级自动验收 |

特别要注意：协议等待表、目录状态和未知操作集合都在内存中。SQLite 资源可以被新建的存储对象重新读取，不代表协议状态已经支持进程崩溃恢复。

第一批故障实验提供了持久化执行意图和双库恢复；本包则集中验证并发与消息边界。两套实验可以互相补充，但目前没有合并成一个生产 Runtime。

## 16 项测试按失败责任划分

| 组别 | 数量 | 关键断言 |
| --- | --- | --- |
| 并发与业务状态 | 5 | 旧版本拒绝、新版本可提交、并发重试只有一个资源、同键异参拒绝、断线不撤销副作用 |
| 初始化与能力 | 4 | 初始化前禁用工具、完成通知后开放、版本不兼容断开、缺少能力拒绝调用 |
| 关联与取消 | 4 | 倒序响应正确关联、取消后忽略迟到响应、初始化不可取消、未知取消不改变状态 |
| 目录与错误 | 3 | 旧目录响应不能恢复缓存、区分协议与工具错误、畸形响应不完成请求 |

这些测试在编写时全部通过。数量描述的是覆盖的契约，不是 MCP 兼容性得分，也不是 Agent 任务成功率。

## 用小改动理解测试为何存在

可以在实验副本中尝试三种变化：去掉更新条件中的版本判断；把工单去重检查移到事务之外并移除唯一约束；允许旧目录响应重新将缓存标为有效。

先预测哪项断言会失败，再运行测试。对并发错误，某些错误实现不一定每次都暴露；应使用屏障控制关键交错，而不是重复运行直到碰到一次异常。实验当前已有的屏障确保两个更新者先读到同一版本。

这一步的目标是建立因果解释：某项机制具体阻止了哪个反例。若移除一个机制后没有相关测试失败，要么测试覆盖不足，要么它并不负责你以为的保证。

## 下一步接入真实服务时保留什么

真实接入应固定 SDK 与协议版本，在本地测试服务器上增加消息编码、分片、异常退出、会话失效和认证失败测试；再接实际写工具，验证业务操作键和权威查询。

当前实验没有实现完整 JSON-RPC 验证、工具分页、双向服务端请求、OAuth、HTTP/SSE、Tasks 或任何模型调用。协议依据来自 [MCP 2025-11-25 生命周期](https://modelcontextprotocol.io/specification/2025-11-25/basic/lifecycle)及各篇所列规范；实验中的保守闸门和目录修订策略属于本文设计。

继续实践：[Harness 接入与实战](/writing/harness-integration-map/)。

## 业务写入恢复实验

第二组实验将任务契约、运行状态和验收接成一个执行骨架：创建资料核验工单，在写入成功后制造中断，再恢复并检查实际结果。

实验使用固定候选动作代替模型，只验证执行契约。这样，同一个故障可以重复出现，不会被模型每次生成不同答案掩盖。它是完整 Agent 的一部分，尚不包含自主规划、真实推理或外部服务。

### 下载后即可运行

[下载实验源码与测试](/labs/harness-engineering.zip)，解压后在目录中运行，要求 Python 3.10+，无需额外依赖：

```sh
python3 lab.py
python3 -m unittest discover -p 'test_*.py' -v
```

如果已取得本站仓库，也可以从仓库根目录执行：

```sh
python3 docs/harness-engineering/lab.py
python3 -m unittest discover -s docs/harness-engineering -p 'test_*.py' -v
```

程序在临时目录创建数据库，演示完成后清理。不会访问真实工单平台、发送消息或修改你的知识库。

### 为什么使用两份数据库

`runs.sqlite` 保存任务契约、运行状态、派发次数与事件。`tickets.sqlite` 代表外部服务，保存实际工单和唯一操作键。两边独立提交，才能制造“工单已存在，本地却没有收到结果”的窗口。

如果把本地状态和所谓的外部写入包在同一个事务里，程序虽然更容易通过测试，却回避了真实接口最重要的失败边界。

固定动作的目标是为 `source-001` 创建“核验 Agent Harness 资料”。任务的预期结果由可信调用方单独传入，验收器读取实际工单再比较。候选动作和预期结果刻意分开，以便构造“动作执行成功，但内容错误”的反例。

### 演示中实际发生什么

默认运行会在工单提交后、工具结果落本地之前抛出受控异常。随后新建 Harness 对象，从同一组数据库继续处理。

关键输出如下；这是固定教学样本的结果，不是模型成功率统计：

```json
{
  "before": {"state": "dispatching", "attempts": 1},
  "after": {"state": "succeeded", "attempts": 1},
  "actual_tickets": 1
}
```

恢复时先查询稳定操作键，找到实际工单，写入 `effect_reconciled`，再记录验收与终态。因此没有消耗新的派发次数，也没有第二条工单。完整输出还会列出事件序列，便于对照。

SQLite 在这里代表一个提供权威查询与原子去重的模拟服务。真实远端“查不到”可能只是尚未同步，不能照搬本地服务的不存在判断。

### 看反例，才能知道通过了什么

| 场景 | 预期观察 |
| --- | --- |
| 正常执行后重复运行 | 一条工单，终态保持成功 |
| 保存意图后、实际写入前中断 | 在剩余预算内继续派发 |
| 外部提交后、本地结果前中断 | 对账恢复，仍是一条工单 |
| 结果保存后或验收后中断 | 重新读取实际资源并结束 |
| 同键换参数 | 拒绝，不创建替代资源 |
| 缺审批、审批过期于当前策略 | 等待匹配审批，不产生写入 |
| 当前策略拒绝 | 拒绝执行 |
| 派发前取消、零预算 | 没有工单 |
| 派发后取消 | 停止新动作，对账后保留已发生影响的记录 |
| 工具写入了错误资料 | 工具成功，但任务验收失败 |

测试还启动独立 Python 子进程，在外部提交后退出，再由父进程恢复。这验证数据库内容确实跨进程保留；它没有模拟磁盘损坏、机器断电或网络分区。

### 实验没有替你证明什么

审批值只是由测试驱动提供的动作摘要；身份和权限是可信输入，不是完整认证服务。数据库文件也没有防篡改保护。这里不验证提示注入防御、凭证隔离、多 Worker 调度或真实租户安全。

预算只记录派发尝试，不记录 Token、费用和墙钟时间。取消只在运行边界检查，没有终止远端在途请求的能力。服务去重依赖一台机器上的 SQLite 唯一约束，不能被描述为分布式 exactly-once。

这些限制决定了测试结论的范围：它证明几条确定性的执行契约在给定模型中成立。模型能否正确准备工单，需要另一组真实任务评测。

### 从执行骨架走向真实 Agent

下一步先把固定 `Action` 换成模型候选，保留任务目标、策略检查、稳定操作键与独立验收器。比较接入前后的无效参数、验收失败和任务成本，避免模型把本来确定的控制责任重新接走。

再替换工单服务，核对真实接口的幂等作用域、查询一致性、去重留存和鉴权。最后才加入并发 Worker、队列、沙箱和跨服务 Trace，每增加一种机制，都新增一个它应该解决的失败样本。已有[评测工程篇](/writing/agent-evaluation-engineering/)可承接这些样本。

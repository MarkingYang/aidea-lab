## 一条连续的论述

总问题：如何从业界对真实工作问题的不同尝试，形成适合自身约束的 Harness 架构与 Agent 产品，并用验证修正选择？

整个体系按下面的认识过程推进；这些是研究责任，不是预先锁定的文章或章节数量：

| 推进位置 | 需要说清楚什么 | 怎样承接后文 |
| --- | --- | --- |
| 工作与对象边界 | 用户委托的工作是什么，Harness 与产品分别承担什么 | 为选择研究对象提供范围，不提前确定模块 |
| GitHub 对象研究 | 对象自己的目标、完整结构、代表任务、关键选择和限制 | 产生待比较问题；保留框架外发现 |
| 产品对象研究 | 具体表面的用户、任务、过程、介入、交付与成本 | 产生产品取舍，不凭界面猜内部实现 |
| 跨对象比较 | 相同问题下有哪些选择，约束和代价由谁承担 | 归纳条件性解释，允许没有统一赢家 |
| 自身任务约束 | 为谁做，接管多大范围，失败后怎样接手 | 使架构与产品的选择具有明确前提 |
| Mini Harness 架构 | 模块责任、接口、运行状态、执行与恢复如何支持有限任务 | 形成工程上可验证的主张 |
| OS Agent 产品 | 委托、资料、成果与协作如何构成可使用的工作流程 | 与架构平级修订行为和承诺 |
| 联合验证 | 正确性、使用效果、人工负担和运行代价 | 回到原段落修订条件与设计，不只添加结尾总结 |

GitHub 与产品研究是认识的来源，不能被要求证明预定架构。控制、上下文、执行、状态、权限和验收是待检验的整理线索；应用组合、分发维护、成果编辑等新维度可直接改变论述。

候选研究对象仍包括 Pi、DeepSeek Harness、Codex、LangChain / LangGraph，以及 Claude Code、Codex、Kimi Code、Kimi Work 的具体产品表面。这不是篇数安排，也不是已经确认的可比样本。逐个进入研究时核定身份、版本、代表任务和证据条件；新发现可改变名单。

## 避免再次失去连贯性

1. 每次修订先读取对应文章的完整正文，明确现有论点和证据边界。
2. 每个研究对象先在一篇完整长文中解释自身。综合文章保留理解比较所必需的背景、关键依据和推导，再链接独立研究供深入阅读。
3. 一个关键定义只在正文有一处完整定义，其他位置使用一致含义。
4. 新证据应修改受影响的论点及后续推导，不能只在末尾追加新章节。
5. 不把“存在接口”“文档声称”“测试定义”“实际运行通过”混为一谈。
6. 只有完成相应研究才填写结论；缺材料时说明当前问题，避免编造竞品能力或实验结果。
7. 取舍必须保留问题、约束、选择、收益、代价和适用条件。分析者提出的备选不冒充团队决策历史。
8. 核心推理留在正文；来源清单、脚本和日志可单独保存，避免重复维护多份论述。

## 六个主要方向的边界

| 方向 | 主问题 | 文章应形成的结果 |
| --- | --- | --- |
| Harness | 模型如何进入可控制、可恢复、可验收的任务系统？ | 职责、控制权、状态与模块接口；完整项目实现及其取舍 |
| 模型 | 模型怎样获得和使用能力，能力受哪些条件限制？ | 架构、训练或推理机制、接口与能力证据；明确未覆盖部分 |
| 技术架构 | 一个工程问题怎样被机制解决？ | 输入输出、状态、主流程、不变量、失败路径与适用边界 |
| 产品 | 谁在什么情境下把什么工作交给系统？ | 用户任务、产品对象、流程、交互、交付标准和价值 |
| 竞品分析 | 面对相同问题，不同对象作出了哪些选择？ | 可比较条件、差异、代价、证据缺口；不伪造综合排名 |
| 技术选型 | 在本团队约束下，采用什么、放弃什么？ | 硬约束、候选、验证、决定、接受的风险与重新评估条件 |

评测是各方向结论的校验手段，也可以有独立论文或机制文章。研究与认知保留陆奇等完整阅读对象。

## 不同文章使用不同分析方式

**GitHub 项目研究**从项目自身的问题出发。固定仓库、提交和范围，说明核心对象与模块，追踪调用链、状态流和异常路径，解释关键设计为什么成立、代价在哪里。代码文件、符号与测试支持具体声明。框架自身的独特设计优先，不能为了填统一表格而略去。

**知识点剖析**回答一个完整问题。先给可判断的定义和最小案例，再解释机制如何改变状态、必须维持什么约束、为何不用其他方案、反例怎样使它失效。例子应揭示机制，不能只给抽象原则换业务名词。

**模型研究**分别检查结构、训练目标、数据与后训练、推理和部署条件。区分模型、工具与 Harness 对结果的贡献；参数量、榜单分数或一次演示不能直接推出使用结论。未公开训练细节保留未知。

**产品研究**以实际用户和任务流程为主线，检查输入、工作空间、任务状态、控制与接管、成果对象和交付价值。界面与公开能力可以观察，内部实现无证据就不推断。源码研究与产品研究可以研究同一品牌，但问题与引用关系应明确。

**竞品分析**先统一问题、对象层级、版本和比较条件，再解释设计差异及代价。产品承诺、源码事实、运行结果分开记录。未完成同题实验时，可以比较结构与定位，不能宣称质量、成本或性能冠军。

**选型分析**先列硬约束，排除不满足者，再验证剩余候选。记录选择理由、放弃项、额外建设、运行成本和退出条件。选择只在这些条件内成立；新证据可以推翻它。

这些是检查视角，不是每篇必须重复的标题模板。

## 知识密度如何验收

每节至少提供一项新内容：机制、可核验事实、因果解释、约束、反例或决策依据。删除一段后，如果读者的理解和决定没有损失，就应考虑删除。

发布前逐篇检查：主问题是否明确；是否解释真实运行而非罗列术语；是否交代数据和状态归属；是否说明关键取舍及代价；重要事实是否有具体证据；是否保留反例和未知；是否通过引用关联相邻文章而不重复正文。

构建通过、字数少或阅读时长合适，都不能单独证明文章已达到深度标准。

## 文章之间怎样形成体系

项目文章提供独立实现事实；知识点文章从多个对象抽象机制，同时保留反例。Harness 与技术架构将机制组合成系统，产品文章解释系统怎样承接用户工作。竞品分析检查不同组合的分歧，技术选型在具体约束下作决定，评测结果再修正项目理解、机制解释和选择。

这是可双向修正的引用关系。顶层分类不能限制项目研究；某个项目无法被现有机制解释时，应修正分类或补充机制，不能裁剪项目事实。每篇只有一个主目录归属，相关性通过正文链接与知识图谱表达。

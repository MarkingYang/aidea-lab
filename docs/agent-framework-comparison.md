# 如何比较两个或多个 Agent 框架：以 Hermes 与 DeepSeek Harness 为例

资料核验日期：2026-09-06。本文依据官方公开文档与仓库说明整理，未部署运行两个框架，也未固定源码提交进行逐行审计。文档支持的机制、分析判断和待实测结果分开记录；后续用于正式选型时，需补齐版本、配置和实验记录。

## 1. 比较要回答什么

一份有用的框架比较，应回答：**为哪类用户、完成哪类任务，选择哪个框架，需要自己补什么，依据是什么？**

保留技术架构、社区生态、商业模式和许可四个视角，再补上任务效果与采用成本。比较过程可以复用为：

**明确场景 → 对齐比较边界 → 记录机制与证据 → 同任务验证 → 形成有条件的选型结论。**

先写一行决策问题，例如：

> 我们要为一个五人团队搭建长期运行的内部助理，需要聊天入口、跨会话知识、受控工具调用和中断恢复；比较 Hermes 与 dsh 在该范围内的实现与维护成本。

“哪个框架更先进”缺少可验收的答案。“哪个更适合承担这项责任”可以被验证。

## 2. 先确定两者为什么可比

Hermes 官方定位强调自托管、跨会话记忆、复用技能和多种通信入口。[官方说明](https://hermes-agent.nousresearch.com/llms.txt)

DeepSeek Harness 官方定位强调通过 Cordis 组合模型、工具、会话、沙箱、循环、调度与 UI 等能力，并提供可直接启动的 Web UI。[官方介绍](https://www.deepseek.com/harness/en/)

因此，可以在“自建 Agent 工作系统”层面比较二者。进一步比较长期助理或运行时二次开发时，必须分别定义任务，避免把一方的主打方向当成全部候选的唯一标准。

| 比较边界 | 要回答的问题 | 必须计入的投入 |
| --- | --- | --- |
| 默认可用系统 | 安装配置后能完成哪些工作？ | 安装、账号、入口接通和初始配置 |
| 扩展后的系统 | 能否满足我们的特定需求？ | 插件、适配代码、测试与维护 |
| 运行内核 | 状态、循环、权限如何组织？ | 替换机制的难度与兼容责任 |

这三个层面的结果分别报告。原生具备一种能力，与花两周开发后具备同一种能力，在功能表上相同，在采用决策上不同。

## 3. 可以直接复用的八维比较表

| 维度 | 应该比较什么 | 证据或验证方法 |
| --- | --- | --- |
| 产品定位与体验 | 目标用户、默认入口、交付物、人工接管方式 | 跑通一个完整任务，记录配置和接管步骤 |
| 技术架构与扩展 | 谁拥有 Loop；模型、工具、状态、UI 的扩展边界 | 官方架构、固定提交入口；实现同一个扩展 |
| 记忆与技能 | 写入、读取、纠错、删除、作用范围和回滚 | 跨会话任务、事实变更、删除传播、技能回归 |
| 执行与可靠性 | 超时、重试、恢复、并发和外部副作用 | 故障注入后检查完成状态与重复执行 |
| 权限与数据边界 | 文件、网络、进程、凭据、日志和授权范围 | 在目标环境测试拒绝、撤权、各执行入口 |
| 社区与维护 | 发布节奏、问题响应、插件兼容、迁移文档 | 规定时间窗与抽样方法，不只统计 Star |
| 商业与总成本 | 框架、模型、工具、托管、支持及维护成本 | 包含失败和重试的账单、部署与维护工时 |
| 许可与采用条件 | 主项目及依赖许可、模型与服务条款 | 固定版本的许可文件和实际使用的服务条款 |

技术栈影响团队维护能力，但 Python 或 TypeScript 本身不能证明产品更好。包数、插件数和支持渠道数也需要说明统计口径与实际可用范围。

## 4. Hermes 与 dsh：已核验的机制和需要补的证据

下表的“待验证”适用于本次比较，没有测过不能写成“没有能力”。

| 比较项 | Hermes | DeepSeek Harness | 还需要验证什么 |
| --- | --- | --- | --- |
| 默认产品形态 | 提供自托管助理、CLI 和通信入口，强调长期使用 [H1] | 提供默认运行方式和 Web UI，可进一步组合能力 [D1] | 首次完成目标任务的配置时间与人工介入 |
| 架构与扩展 | 模型提供商有注册与插件机制，不能概括为“不可扩展单体” [H2] | Cordis 管理组合；具体 Loop、工具等能力由相关包实现 [D2] | 增加相同工具或替换相同策略的开发、回归与升级成本 |
| 跨会话记忆 | 有持久记忆文件，并在会话开始时注入快照 [H3] | 会话历史由事件日志组织；这不等同于用户长期记忆 [D3] | 同一个用户事实如何保存、更新、删除与再次使用 |
| 技能维护 | Curator 维护技能生命周期，包含归档、审阅与修补机制 [H4] | 文档有技能发现与加载能力；本次未核验与 Curator 对等的自动维护闭环 [D4] | 生成的技能是否有用，维护后是否造成回归 |
| 模型接入 | 支持多种提供商和自托管端点 [H5] | 模型适配器有可扩展接口 [D2] | 同模型的工具调用、流式输出、上下文与错误处理兼容性 |
| 历史与恢复 | CLI 提供 continue/resume 入口 [H6] | Session 使用追加事件日志，持久化是独立机制 [D3][D5] | 杀进程后丢失多少状态，是否重复写入外部系统 |
| 权限与隔离 | 本次未对目标部署的执行边界进行验证 | 有按调用解析的沙箱策略接口 [D6] | 两者都要在目标 OS、后端与插件配置下测试，不能据文档数量排名 |
| 版本与维护 | 本次未建立发布、缺陷与升级的长期样本 | 官方明确标为开发者预览，提示兼容性破坏 [D7] | 版本升级后状态、插件和工作流是否仍能使用 |
| 许可与成本 | 主仓库标为 MIT；可选模型和工具服务另有成本 [H5][H7] | 主仓库标为 MIT，并列出第三方声明 [D7] | 实际依赖、服务使用条件、基础设施和维护成本 |

## 5. 对原始材料的修订意见

| 原说法 | 处理 | 更准确的写法或核验要求 |
| --- | --- | --- |
| Hermes 的 GEPA 是默认自进化引擎，100–500 次即可收敛 | 暂不采用 | 本次未找到足以支持这组归因和数字的官方证据；需给出实现入口、启用条件、评测任务和原始结果 |
| Hermes 越用越强、越用越懂你 | 改为机制说明 | 有持久记忆和技能维护机制；效果是否持续改善，要用固定任务与独立验证集测试 [H3][H4] |
| Curator 自动从所有经验中创造技能 | 缩小描述范围 | 官方将其描述为技能维护流程；技能创建、使用与维护应分别说明 [H4] |
| dsh 必须自己从零拼装 | 修正 | 提供默认使用入口；插件架构提供进一步替换和组合能力 [D1] |
| 只有 dsh 模型无关，Hermes 核心封闭 | 修正 | Hermes 也支持多提供商及提供商插件；应比较各层具体扩展边界 [H2][H5] |
| 100% 单文件测试覆盖率 | 暂不采用 | 需注明 commit、覆盖的文件、行/分支指标、排除规则及报告；不能外推全仓库或任务成功率 |
| 4 天 12.9 万 Star、24 小时 288 插件、321+ 插件 | 暂不采用 | 需要对应历史快照、统计时间、去重规则，以及官方、第三方、兼容可用插件的区分 |
| 半年历史意味着成熟稳定 | 改为待验证 | 项目年龄不能替代版本兼容、故障恢复、维护响应与生产任务证据 |
| 无遥测、无追踪、数据全本地 | 拆开核验 | 本地存储、远程遥测和模型/工具请求的数据去向是不同问题；配置云服务时不能承诺数据全本地 [H5] |
| 本地模型零成本，API 只需每月 5–100 美元 | 修正 | 不作未经测量的费用承诺；本地推理仍计硬件、电力、运维，云调用计失败、重试和辅助模型 |
| MIT 因而所有商用合规问题都解决 | 修正 | 主项目许可只是采用条件之一；依赖、模型、连接器和服务条款分别核验 [H7][D7] |
| Hermes 做前端，dsh 做执行层即可结合 | 改为集成假设 | 需定义唯一的任务负责人、记忆写入方、授权边界、取消传播、恢复和费用归属；本次未验证集成方案 |

这里的“未找到支持”只描述本次证据范围，不代表已证明该说法为假。

## 6. 两个框架怎样做公平实测

将实验分成两组：

1. **共同条件测试**：固定模型及提供商、输入快照、工具权限、资源与预算；考察框架机制差异。无法统一的条件明确记录。
2. **实际采用配置测试**：各框架使用团队愿意长期维护的配置；将配置、插件开发和后续维护投入一并计入。

两组结果不混为一个排名。前者帮助解释差异，后者帮助决定采用。主模型以外的压缩、技能维护和子任务模型也要记录。

### 四个最小验证任务

| 任务 | 统一输入与验收 | 关键指标 |
| --- | --- | --- |
| 重复研究助理 | 给定一套固定资料与引用要求，跨会话交付简报，再修改一条用户偏好 | 引用正确率、偏好更新正确率、人工修正分钟数 |
| 增加内部工具 | 接入同一个只读模拟 API，验证正常、超时、无权限响应 | 开发工时、修改核心文件数、错误处理与回归结果 |
| 中断后继续工作 | 在模拟写入成功但回执未记录的位置终止进程，再恢复任务 | 完成状态、重复副作用次数、丢失状态与恢复耗时 |
| 权限变化 | 撤销某项文件或网络权限，再从各工具入口尝试同一操作 | 是否在执行层拒绝、有无替代路径绕过、日志是否可解释 |

首次试点可用每类至少三个任务、每任务三次独立运行来发现问题。这只是探索性样本，不足以承诺生产可靠性；后续样本量按风险和结果波动确定。

对于“学习效果”，另设训练任务与未见过的验证任务；比较新安装状态与积累技能后的状态。冷启动任务应重置状态，长期学习任务应按预定顺序保留状态。不要把验证答案留在记忆中，再把复述答案记为能力提升。

### 结果记录模板

```yaml
# 研究记录格式，不是 Hermes 或 dsh 的配置文件。
candidate: hermes-or-dsh
version_or_commit: 待填写
captured_at: 待填写
deployment: 待填写操作系统与执行后端
configuration_hash: 待填写
model_and_provider: 待填写完整模型标识与端点类型
auxiliary_models: []

input_snapshot: 待填写
state_policy: fresh-or-preserved

forbidden_actions: []
budget: { minutes: null, currency: null, max_cost: null }
acceptance: []
result:
  status: not_run
  accepted: null
  human_minutes: null
  elapsed_seconds: null
  total_model_and_tool_cost: null
  duplicate_side_effects: null
  permission_violations: null
  trace_and_artifacts: []
```

报告同时呈现验收完成率、人工时间、端到端耗时、恢复与违规情况。单次成功成本用“全部尝试的总成本 ÷ 验收成功数”，包括失败和重试；成功数为零时标为不可计算，并保留总支出。

总拥有成本另算部署、基础设施、可选订阅、扩展开发、维护、升级和迁移费用。样本实验成本与年度预测分开，预测必须公开任务量和工时单价假设。

## 7. 从两个框架扩展到多个框架

新增第三个、第四个框架时，为每个候选填写相同的独立记录，再生成矩阵。无需为所有候选组合反复撰写两两比较报告。

| 能力项 | Hermes | dsh | 候选 C | 验收条件 |
| --- | --- | --- | --- | --- |
| 跨会话偏好 | 机制已核验，待实测 | 目标方案待核验 | 未核验 | 更新后下一会话不再使用旧值 |
| 会话恢复 | 入口已核验，故障语义待测 | 日志与持久化机制已核验，故障语义待测 | 未核验 | 在规定故障点恢复并核对外部状态 |
| 模型扩展 | 提供商机制已核验，目标模型待测 | 适配器机制已核验，目标模型待测 | 未核验 | 同一模型通过工具调用契约测试 |

每个单元格拆成两个字段：

- **实现方式**：原生、官方扩展、第三方扩展、自研、明确不支持、未知。
- **证据状态**：官方说明、源码核验、实测通过、实测失败、未核验。

“官方说明 + 原生”不等于实测通过；“未知”也不等于零分。完整证据记录还应包含来源、版本、日期、适用配置和验证产物。

先用部署环境、必要能力、权限和许可等硬条件筛选候选，再比较任务效果和成本。只有需要汇总评分时才设置权重，并在试验前定义每项分数的含义、归一化方式和缺失值处理。改变合理范围内的权重后如果赢家频繁变化，应报告选择对偏好的敏感性。

若未来做成交互页面，默认保留框架选择、场景切换、只看差异和展开来源四项功能。宽矩阵可以选择二至四个候选并排查看；更大的候选池先筛选。界面应优先展示决定采用的差异及证据。

## 8. 当前能形成的选型判断

以下是根据文档机制形成的采用假设，尚非实测结论：

| 使用目标 | 优先验证方向 | 改变判断的证据 |
| --- | --- | --- |
| 长期个人助理，重视偏好、记忆与技能积累 | 先验证 Hermes 的目标入口与长期任务体验 | 记忆纠错、技能回归或日常维护成本未达到要求 |
| 自建运行平台，重视替换模型、工具、循环或 UI | 先验证 dsh 的扩展边界与升级成本 | 所需扩展仍需大量修改核心，或兼容迁移成本不可接受 |
| 企业生产环境 | 两者均进入同一权限、数据和恢复验证流程 | 用目标环境实测与维护证据决定，不由产品定位直接授予“企业级”结论 |
| 组合使用 | 先证明单框架无法经济地满足需求，再做最小集成验证 | 双重状态、权限或恢复的维护成本高于收益 |

最终决定采用下面这类句式：

> 在【任务范围】、【固定版本与配置】和【权限边界】下，采用【候选】。它在【实测指标】上达到门槛；我们接受【额外开发与维护成本】。当【版本、任务量、数据要求或故障指标】变化时重新评估。

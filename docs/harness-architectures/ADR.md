# 架构决策记录

## ADR-001：单 Worker 起点选择显式循环

情景：核对两份材料，批准后创建一张工单；没有跨服务的长期等待要求。

决定：A 为当前起点，模型／工具／验收用小接口分开，运行和业务分别保存。B、C 为有明确新增需求时的候选。

理由：任务只有有限状态，自写控制成本可见；引入新框架尚未减少必须维护的业务规则。共同实验表明三者在当前样例都能满足相同契约，因此不据此声称其中一个更可靠。

代价：等待入口、状态版本、预算和恢复逻辑由应用维护。A 的样例不能直接暴露为多用户服务。

重新评估：多个批准分支和汇合难以维护时比较 B；任务需要脱离应用进程持续运行或跨服务接管时比较 C。用具体失败与维护成本触发，不设没有数据依据的任务数量阈值。

## ADR-002：业务操作身份独立于控制引擎

决定：操作键、原始参数、幂等创建与资源查询不依赖某个框架。模型只产生业务提案。运行记录与工单不假装属于同一事务。

证据：响应丢失场景下 A/B/C 均先查询已提交工单，最终只有一条资源。不同参数复用同键被拒绝。

代价：业务端必须支持查询和原子去重；换成不提供这些能力的 SaaS 时需重新设计，不能照搬保证。

## ADR-003：明确每层的等待与重试所有者

决定：A 由调用方重新启动；B 由 interrupt / resume 表达等待；C 由 Workflow 等待批准 Signal，Activity 对可恢复异常至多尝试两次。这个上限是实验参数，不是生产建议。

C 与 B 组合时，由外层工作流承担长期等待与整体生命周期，局部图承担有界决策。不能在两个状态系统各保存一份未经定义的批准状态。

迁移：保留旧任务契约与操作键，先跑隔离对照；旧任务排空、显式迁移或明确结束后新建。同一任务同时只有一个写入所有者。代码回退不撤销业务资源。

这里混合了三种东西：研究对象（模型、产品）、技术问题（Harness、技术架构）、分析方法（比较、选型、评测）。因此同类对象被分散，阅读入口也不能清楚说明文章是在解释实现、比较方案，还是研究用户价值。

严格按三类重新判定现有正文的主归属，结果是技术框架 43、模型 2、产品 15。这个数量是迁移建议，不是已应用的导航，也不是未来篇数目标。产品 15 篇中有两篇研究同一个 Claude Code、十篇方法文章、两篇竞品比较和一篇陆奇阅读；模型 2 篇分别是能力综述与选型方法，尚无以单个具体模型为对象的完整深析。数量不能代替覆盖度。

## 三个顶层，以及各自的分析方式

| 顶层 | 核心问题 | 内部文章类型 | 必须保留的边界 |
| --- | --- | --- | --- |
| GitHub（技术框架） | 系统如何构成、运行，为什么这样设计？ | 项目研究、知识点深剖、技术架构比对、设计与实现、评测方法／论文 | 公开源码、文档归纳、设计建议、实际实验分别说明；GitHub 是证据入口，不是所有仓库都有同一种架构 |
| 模型 | 模型通过什么机制获得哪些能力，在什么条件下可用？ | 单模型研究、模型机制、同题比较与选型 | 模型与 Harness 的贡献分开；未公开的训练或架构细节保留未知 |
| 产品 | 谁把什么工作交给系统，如何接管与验收，价值在哪里？ | 单产品研究、产品竞品分析、产品设计与采用方法 | 用户界面与公开承诺不推导内部实现；分析原型不冒充用户调研，体验建议不冒充实测 |

“技术架构比对”“产品竞品分析”“知识点深剖”“评测”均作为文章类型或方法，不再设为第四、第五个顶层。

为了让读者有明确入口，建议三类内部这样组织：

```text
GitHub（技术框架）
  项目研究：每个仓库／明确技术对象一篇完整研究
  知识点深剖：以问题建立入口，引用项目中的证据
  技术架构比对：同一任务下解释候选设计的取舍
  设计与验证：参考实现、故障实验、评测与论文

模型
  单模型研究
  模型机制
  模型比较与选型

产品
  单产品研究
  产品竞品分析
  产品设计与采用方法
  阅读补充：保留陆奇，不将其伪装成产品实测
```

这是目标组织方式。没有内容的入口先不展示；不通过创建空栏目假装补齐。

## 三类不能共用一张内容模板

### GitHub 技术框架

从项目要解决的问题出发，固定版本和研究范围，追踪核心对象、模块接口、一次正常执行、一次异常执行、状态如何保存和恢复，再解释取舍与采用条件。

验收至少要求：读者能从入口追踪到结果；能定位关键决定由哪个模块作出；知道一种失败为何发生及如何处理；知道哪些责任仍留给宿主。不是每篇都必须跑完整生产系统，但机制结论必须有匹配的证据。

LangGraph 的重点可以是超级步与通道，Temporal 是事件历史与 Activity，OPA 是求值结果与执行点，LiteLLM 是部署选择与回退。不能要求它们各自填出不存在的 Agent Loop、Memory 或 RAG 模块。

### 模型

固定模型标识、版本、开放范围与推理配置；从公开资料分析结构、训练／后训练、输入输出能力、推理和部署要求；再用相同任务研究质量、时延、资源和成本。闭源模型的内部机制只写公开事实。

模型文章不能只是一张最新排行榜。应能回答：它为什么可能适合某类任务，实测是在什么 Harness 与预算下得到的，优势在哪些条件下消失，以及迁移会改变哪些接口或运行条件。

Prompt Engineering 主要归技术框架的使用机制；需要解释训练、推理或模型特定行为时，再链接到模型研究。Embedding／Rerank 的模型机制归模型，其在 RAG 管线中的组合归技术框架。

### 产品

固定产品版本、入口、套餐和使用环境；明确用户、任务、工作对象、主流程、失败与接管、成果验收、扩展与治理，再解释价值和采用代价。

产品文章应至少追踪一项完整任务，并说明实际观察与作者分析的区别。功能数量、最大并发量、是否有连接器，都不能单独替代用户任务结果。

同一品牌可以有技术与产品两篇：例如开源 CLI 的执行内核与桌面工作台的用户流程。但必须是两个不同研究问题，不能在两篇里重复循环、记忆和权限的相同概述。

## 九个重点知识：现状、边界与补强

以下使用工作定义来组织本站知识，不宣称是行业统一分层。“已有”描述内容覆盖，不代表所有相关生产行为已经实测。

| 知识点 | 应回答的完整问题 | 现有依据 | 评审与下一步 |
| --- | --- | --- | --- |
| Prompt Engineering | 如何把任务目标、示例、约束和输出要求变成可检验的行为接口？ | Harness 篇的购物车示例；Skills 与 Hermes 中的指令组织 | 有基础定义，缺系统深剖。补提示结构、示例选择、歧义／冲突、结构化输出与失败样本；固定材料和模型比较提示版本，不能把长提示当成质量证据 |
| Context Engineering | 本轮输入怎样选择、装配、压缩、排序与失效？ | 上下文组装；OpenCode、Kimi Code 的投影／压缩；Haystack 的证据注入 | 已有机制和源码反例。补实际序列化请求、Token 计量、压缩前后证据保留、权限／版本变化下的失效；区分持久历史与模型可见视图 |
| Loop Engineering | 每次反馈如何改变下一步，何时继续、等待或终止？ | Agent 控制流中的状态、预算、停滞、取消与重规划 | 已有较完整分析。保留整篇；去除前后重复定义，关联真实项目的执行轨迹；别把“计划写了什么”当作运行状态 |
| Graph Engineering | 依赖、调度、分支、汇合和状态更新怎样形成可执行结构？ | 同一控制流篇；LangGraph 的超级步／Reducer；Haystack 的 Join；架构对照实验 | 已有深度，不应标为空白。建立直达章节的知识入口，统一 DAG 与有环执行图、条件分支与汇合、重试与重复合并的区别 |
| Harness | 模型、上下文、控制、执行、权限、持久状态与验收怎样共同完成任务？ | Harness 架构、Mini Harness 实战、架构选型及多个运行项目 | 覆盖较强。明确架构定义、参考实现和选型各自的问题；采用条件必须能追溯到项目或实验，避免预设所有系统必须拥有同一组组件 |
| RAG | 原始资料如何变成可检索证据，并支持生成与答案验收？ | Haystack；记忆检索；上下文组装 | 局部较强，完整主问题不足。补摄取／解析／切分、索引更新、查询改写、召回／融合／重排、引用与拒答，分别评测检索和生成；现有无 LLM Pipeline 实验不能证明答案质量 |
| Agent Runtime | 一项 Agent 任务在进程中如何运行、挂起、取消、恢复与释放资源？ | Pi、OpenHands SDK、OpenCode、Kimi Code、Temporal 等 | 证据分散。需围绕 Run／Session／Event／Action 的关系建立完整机制分析，讲状态所有权、并发、事件顺序、恢复与资源生命周期；不把 Runtime 等同 Loop 或工作流服务 |
| Memory | 什么值得长期保留，怎样表示、纠错、召回、遗忘和控制共享？ | 三个项目；写入、检索、治理三篇；记忆比较 | 内容广但重复项目介绍。建议评估整合三篇机制为一个连续的 Memory 问题，保留原链接与锚点；保留时间语义、来源依赖和撤权，而不是压缩成功能表 |
| LLM Gateway | 如何选择合格部署，维持协议、回退、预算与输出边界？ | 模型网关机制；LiteLLM 固定版本研究 | 已有较完整机制。迁入技术框架。后续只为明确缺口补真实适配／流式／共享预算验证，不重复写一篇网关概览 |

它们通过职责关联，而非术语上下包含：Prompt 设计指令；Context 管本次完整输入；Loop 管反馈迭代；Graph 管依赖和交接；Runtime 执行与保存过程；Harness 将这些能力与环境、权限和验收组合。RAG、Memory、Gateway 按任务需求接入，均不是每个 Agent 必装的组件。

执行图与知识图谱不是同一对象；RAG 不等于 Memory；Session 历史不等于长期记忆；模型网关不等于模型；这些区别必须贯穿目录、标题和正文。

## 比较文章需要真正解释取舍

### 技术架构比对

先固定问题与约束，再比较控制方式、状态归属、接口、故障恢复、部署代价及替换条件。对固定任务运行相同正常路径和故障样本；没有同题性能结果时，只比较实现语义。

现有 [Harness 架构选型](../../src/content/writing/harness-architecture-selection.md)是较好的起点：三种真实控制引擎使用同一业务契约，并明确固定模型替身与服务端灾难恢复未测。它应放技术框架内，不必再建选型顶层。

现有记忆比较主要给出对象、生命周期维度与候选原型，尚不足以独立支撑具体选型。应把一项时间纠错与撤权任务贯穿三个项目，比较责任转移在哪里，再给出有条件的采用判断。

### 产品竞品分析

比较用户任务、工作对象、流程、接管、交付物、扩展、治理、维护与退出成本。产品版本和入口必须可比；本地 CLI、云端服务、桌面 App 的能力不能无条件合并。

现有 Coding Agent 对比的标题是“Harness 分歧”，正文却明确研究公开产品结构，包含入口、用户体验、协作与生态。建议按当前实质归产品竞品，并调整标题与判断口径；不能因名字包含 Harness，就视为源码架构比对。

现有办公竞品比较已有任务契约和反例，但明确尚无同题租户实测。应保留这种边界；下一步补产品任务记录，而非继续扩展品牌列表。

### 比较应回到三个问题

1. 同一个约束，各对象作出了什么不同选择？
2. 每种选择把复杂度或责任放到了哪里？
3. 什么证据会改变当前采用判断？

只有功能名称和“优缺点”两列的文章，无法完成这三项论证。

## 后续工作的最小顺序

第一步，按逐篇归属表迁移导航，保留文章正文、URL、日期和来源；旧专题路径需重定向或保留入口。先完成分类，不借迁移批量删文、合并或补写。

第二步，修复确定的结构问题：模型选型篇的章节断裂、比较标题与内容不符、旧图说明；核对现有 Codex／Skills 的证据标签。Claude 与 Memory 的整合先确定连续论证及旧链接映射，再逐篇实施。

第三步，优先补 Prompt、RAG、Agent Runtime 三个完整知识问题。它们可以引用现有项目，不预先要求各新增一篇；先判断现有文章能否承接完整论述。Loop／Graph 保持完整，不因有两个标签强行拆分。

第四步，补一个明确模型版本的完整分析和一个现有比较对象的完整产品研究，然后用同题证据修订比较文章。具体对象按来源可得性与任务代表性选择，不在此凭空定性能冠军或强行定篇数。

每篇采用共同证据门槛、不同论述结构：有清楚问题，有可追踪机制或流程，有取舍与反例，有验证及限制，有回到相邻文章的实质联系。参考文献多、测试数量多或阅读时间长，都不单独构成深度。
